## Not tested

- Restoring to a **past** point in time (only head was restored). It uses the
  same history, which reaches back 6 hours on this plan.
- Neon *instant restore* onto `main` itself — the step that would put a
  recovered state into service. Not done, because it overwrites production.
- Uploaded document **files**: there is no backup of the Blob store to
  restore from. Only their metadata was verified.
- Re-creating secrets, or a lost Vercel project. Secrets were not used: the
  test generated its own `BETTER_AUTH_SECRET`, so existing two-step sign-in
  could not have worked on it.
- Signing in as a real user (no real credentials were used).
- The browser front end; the API it uses was tested.

## Weaknesses found

1. Production's Neon project is on the Free plan: **6 hours** of history, no
   snapshots, no `pg_dump` exports. No copy of the database exists outside
   Neon.
2. No backup of uploaded files.
3. Sensitive Vercel variables cannot be read back; nothing records them
   elsewhere that this test could confirm.
4. This machine's network policy blocks Neon hosts, so the app test needed a
   Vercel Sandbox. A future tester on an ordinary computer can run
   `npm run dr:smoke` directly.
